## 🔴 blocking(P0 の前に決める)

### B1. `send` の手順 2 は CLI から実装できない(§7)
- 何が問題: `send` は Bash から呼ぶ CLI。だが `SendMessage` は**セッションの中のツール**で、シェルから呼ぶ手段は文書化されていない。inbox ソケットへの直接投函は wire format 非公開で、research は「外から叩く設計は避ける」と結論している(research §2)
- さらに悪いことに、生きている席に `claude --resume <id> --bg "<msg>"` を打つと、**起きるのではなく「コピー」が作られる**(research §2)。つまり生きている席に CLI から届ける正規の手段が今は無い
- なぜ効くか: PM → メンバー、メンバー → PM の全配送がこれに乗る。ここが崩れると §7 と §8 が全部書き直しになる
- 候補(検証で選ぶ): (a) 送る側のエージェントが `send` で記録したあと、自分で `SendMessage` ツールも呼ぶ(2 段の規律) (b) 各席に `asyncRewake` フックか Monitor を置き、自分の inbox.jsonl を見て自分で起きる (c) メンバーは `claude -p` の使い捨てにして「生きている席に届ける」問題自体を消す(→ B5)
- ❓ user への質問: 配送は「エージェントの規律(a)」「席側の監視(b)」「メンバーを使い捨てにする(c)」のどれで行くか。検証結果を見てから決めてよいか

### B2. 無人の席の権限モードが書かれていない(§4.1「権限」の一語だけ)
- 何が問題: どのモードを選んでも穴がある
  - manual / default: 承認待ちで止まる。**未 attach の background ではダイアログが無期限に開いたまま**(research §2 N1)。しかも「ダイアログ待ち」は 1h 停止の対象外なので、誰にも気づかれず常駐し続ける
  - bypassPermissions: 人が見ていない席が `rm -rf`・`git push --force`・秘密情報の送信をしても止めるものが無い
  - auto: classifier が止めてくれるが、送信する `SendMessage` も審査対象(research §6)。ブロックされた時の挙動は未確認
  - `--permission-prompts none`(承認が要るものは即 deny)は docs 上 `-p` 用。**`--bg` で効くかは未確認**
- hold との関係: `crossSessionInbound: accept` は入れる予定だが、人間の対話セッション(非 bypass)とチーム(bypass)が混在すると、未設定の席では黙って滞留する。hook・settings が resume 後も残るかも未検証(§4.1 の【要検証】)
- 注入リスク: 調査チームは Web の文章を読む。それを `send pm` で PM に渡し、PM が merge 権限を持つと、外部テキスト → 権限のある席、という経路ができる
- ❓ 質問: 席の既定モードはどれか(推し: auto + 破壊的コマンドの deny ルール)。「人間が見ていない間は絶対にやらせない操作」の一覧を誰が持つか(team.yaml? 共通設定?)

### B3. 「シフトの終わり」が実体として定義されていない(§8.1・§8.3)
- 何が問題: background session は**ターンが終わってもプロセスが終わらない**(spike Q4)。`per_task` の「仕事が終わったら終了」を誰が実行するのか書かれていない
  - 席が自分で `claude stop <自分の id>` を打てるかは未検証
  - 誰も止めなければ 1h 放置で supervisor が止める → その間 roster は「生きている」、`send` は古いシフトに届く
- 矛盾: §7 手順 3 は「止まっていれば `--resume` で再開」だが、`per_task` は「割り当てごとに新しいセッション」。止まった per_task の席に新しい仕事が来たら、resume するのか新規か、ルールが無い(resume すると前の仕事の会話全体を再送するので高い)
- ❓ 質問: per_task の席は「終業で自分を stop する」でよいか。`send` は per_task 宛てなら常に新規起動、persistent 宛てだけ resume、で割り切ってよいか

### B4. 稼働時間の上限が「唯一の暴走止め」なのに、タイマーが一番もろい(§12.1)
- 何が問題: 「team up で一度きり仕掛ける」タイマーは、要するに**数時間 sleep し続けるプロセス**。これをどこで動かすか書かれていない
  - admiral の Bash の background で動かす → admiral のセッションが止まれば一緒に消える
  - nohup で切り離す → それは §2 が禁じた常駐プロセスそのもの
  - 消えても誰も気づかず、チームは上限なしで走り続ける(予算上限は外したので、他に止めるものが無い)
- ❓ 質問: 終了時刻を「プロセス」ではなく「データ」(`.runtime/deadline`)として持ち、席側の hook(SessionStart・Stop)や `send` が毎回それを見て止める方式にしてよいか。この方式ならタイマーが消えても上限は効く

### B5. もっと単純な形を一度検討してほしい(全体)
- メンバーを `claude -p`(使い捨て)で起動し、PM だけを常設の background 席にする形
  - 得るもの: B1(生きている席への配送)がメンバー側で消える / `--permission-prompts none` と `--max-budget-usd` が正式に使える / 終了時に `total_cost_usd` が返るので使用量が見える / プロセスが自然に終わるので B3 も消える
  - 失うもの: メンバーの実行中に attach して割り込めない(終了後 `--resume` で開くことはできる。メッセージは実行中も受けられる)。zellij でメンバーの席を覗く価値が下がる
  - 注意: `-p` の既定が将来 `--bare`(サブスク認証不可)になる予告あり。明示フラグで守る必要がある
- ❓ 質問: 「メンバーの作業をリアルタイムで覗いて割り込める」ことに、上記を捨てるだけの価値があるか。無いなら P0 はこの形の方がずっと小さい

## 🟡 important(P1 の前に決める)

### I1. 並行書き込みのロックが無い(§6・§7)
- board コマンド、inbox.jsonl の既読管理、roster.json は、複数の席・`send`・タイマーが同時に読み書きする。「既読の管理は inbox 側」は、追記中のファイルを書き換えることになり、取りこぼしが起きる
- ❓ 1 本のロックファイルで直列化する(最小)でよいか。既読は別ファイルのカーソル(何行目まで読んだか)で持つか

### I2. 実装者 2 人の競合と merge が宙に浮いている(§5・§4)
- background session は既定で**自分で commit・push・draft PR まで作る**(research §6)。チームの git 規律を CLAUDE.md で上書きしないと、PM の割り振りと関係なく PR が乱立する
- `decisions.merge: owner` で owner が不在なら PR が溜まり、後続タスクが古い main から分岐して衝突が増える。conflict を誰が解くかも書かれていない
- per_task の実装者は毎回新しい worktree で起きる。レビュー指摘を直す 2 回目のシフトが、前回のブランチに戻る手順が無い(handoff に PR 番号があるだけ)
- ❓ merge の既定は誰か。conflict 解消は誰の仕事か。「タスク = ブランチ」を board の固定項目にするか

### I3. 自動 worktree と記録フォルダの関係が未検証(§4.1・§6.1)
- background の隔離は「編集前に worktree へ移動し、以後隔離を強制」。`--add-dir` のチームフォルダへの書き込みが許されるかは未確認
- **調査チーム(cwd = チームフォルダ)で、チームフォルダを git 管理すると、席がチームフォルダの worktree で動き、記録がコピー側に書かれてばらける**可能性がある。§6.1「git 管理は利用者次第」とぶつかる
- 自動 worktree は `.claude/worktrees/` を**作業対象の repo の中**に作る。§4.1「作業対象の repo に書き込まない」と表現が矛盾する(実害は小さいが明記が要る)
- ❓ repo の無いチームは `worktree.bgIsolation: none` 固定でよいか

### I4. captain が単一障害点で、しかも黙って止まる(§3・§8・§12)
- PM が止まる(1h ルール・メモリ逼迫・再起動)と、メンバーからの `send pm` が来ない限りチーム全体が止まる。日報も来ないので owner は翌日まで気づけない
- PM がループする(同じ指示の送り直し、メンバーとの往復)のを検知する仕組みが無い。3h の中で枠を使い切りうる
- persistent の PM はメンバー全員の報告が集まるのでコンテキストが一番膨らむ。入れ替え条件が【未決】のまま(§15)。resume するたびに長い会話を再送するので高い
- 席が作業途中で落ちると、board の項目は `active` のまま残り、PM は気づかない
- ❓ PM の生存を誰が見るか(admiral の `team status`? 最低限「最後に動いた時刻」を出す)。persistent をやめて PM も「起きるたびに記録から立ち上がる」形にしてよいか

### I5. 記録が数週間で崩れる箇所(§6)
- **memory 候補が消える**: 候補は handoff に書くが、handoff は毎シフト上書き。週次の棚卸しの時点で、前のシフトの候補はもう残っていない
- **`count: 2` の席の記録が衝突**: `roles/<role>/handoff.md` は役割に 1 本。impl-1 と impl-2 が同じファイルを上書きし合う。席(impl-1)と役割(impl)の区別がフォルダ構成に無い
- **per_task の handoff は意味が薄い**: 次の per_task シフトは別の仕事をする。仕事の続きは board 項目の本文の方に書くべきでは
- **起動時の読み込み量の上限が守られない**: inbox の未読と「自分の担当」ビューには上限が無い。数日止めたあとの未読が全部入る。SessionStart の additionalContext の長さ制限も未確認
- **週次の棚卸しは PM に重すぎる**: 全役割の memory を PM が書く = PM が実装の細部まで理解している前提。PM のコンテキストをさらに圧迫する
- ❓ memory 候補は `roles/<seat>/memory-inbox.md` に追記で溜めるか。handoff は席ごとか、タスクごとか

### I6. 人間がメンバーの時の返信経路が無い(§3・§7・§9)
- §3「人間もエージェントと同じ宛先」だが、人間が**返信する**経路は「PM の席に attach して話す」だけ(§9)
- 人間が PM 以外の役(例: reviewer)を担う場合、仕事の受け取り(通知 → inbox を読む)と返信(`send` を人間が打つ?)が決まっていない。memory には「user はシェルコマンドを打たない」とある
- PM が止まっていると、attach で蘇る(spike Q4)。これは便利だが §10 の「生きている席にしか attach しない」と逆向きの使い方で、どちらを正とするか明記が要る
- ❓ 人間はどこで仕事を受け取り、どこで返事をするか(スマホから?)。当面「人間は PM とだけ話す」に絞ってよいか

### I7. 使用量が見えない(§12.1・§14・§16 P3)
- 予算上限を外したのはよいとして、**見る手段まで P3 に回っている**。3h × 5 席の消費がどれくらいか、サブスクの枠(5 時間枠など)に当たったとき席がどうなるか(待つ? 失敗する? PM は気づく?)が不明
- ❓ P0 で「シフトごとに使ったトークン量を 1 行残す」だけでも入れるか(transcript から数える / `-p` なら `total_cost_usd`)

## 🧪 P0 で最初に検証すること(この順で。どれかが NG なら設計が変わる)
1. **CLI → 生きている席への配送**: 席の中で `asyncRewake` フック / Monitor が inbox.jsonl の追記で起きるか。送る側が SendMessage ツールを呼ぶ方式と比べる(B1)
2. **無人の権限**: `--bg` で `--permission-prompts none` が効くか。auto mode で危険コマンドが止まったとき、席はどうなるか(固まる? deny して続く?)(B2)
3. **起動フラグの持続**: `--settings`・`--agents` JSON・hooks・`crossSessionInbound` が `--resume --bg` と supervisor 再起動のあとも効くか。`--agent <name>` が `--agents` JSON の名前を解決できるか(§4.1 の【要検証】+α)
4. **自己終了**: 席が Bash から自分を `claude stop` できるか。できないなら per_task の終わらせ方を変える(B3)
5. **worktree と記録**: 自動 worktree に移った席が `--add-dir` のチームフォルダに書けるか。git 管理のチームフォルダを cwd にした席がどこに書くか(I3)
6. **1 往復の最小ループ**: PM 1 席 + impl 1 席で、task 1 件を「割り振り → 実装 → 報告 → PM が次を決める」まで無人で通す。board は固定項目だけ、zellij・日報・memory・3 段停止は入れない。このときの使用量も記録する(B5 の比較材料にもなる)
